## 二、潜在问题

### 2.1 性能问题

| 位置 | 问题 | 影响 |
|------|------|------|
| `L1056` applyMapping() | 使用 `XSSFWorkbook` 读取整个文件到内存 | 大文件会 OOM；与 processExcel() 使用 SXSSF 不一致 |
| `L1104` applyMapping() | 每行都调用 `SwingUtilities.invokeLater()` 更新进度 | 大文件时 EDT 被高频调度，UI 卡顿 |
| `L1158` applyMapping() | 每行都 `invokeLater` 更新进度条（同上） | 10 万行 = 10 万次 EDT 调度 |
| `L1343` processExcel() | `templateHeaders.indexOf()` 在内层循环中线性查找 | O(n*m) 复杂度，应预建 Map |
| `L1224-L1225` processExcel() | 通过 `getComponent(0)` 硬编码获取进度条组件 | 脆弱的 UI 组件引用方式 |

### 2.2 可维护性问题

| 问题 | 详情 |
|------|------|
| **ExcelTools.java 2074 行** | 5 个 Tab 的 UI 布局、事件处理、核心逻辑、数据模型全在一个类中，任何修改都容易产生副作用 |
| **createCrossSheetPanel() 内联 300 行** | 跨表填充的完整 UI + 事件处理 + 业务调用全部内联在方法中，没有拆分 |
| **createDuplicateColPanel() 内联 150 行** | 同上，重复列合并的 UI + 事件 + 调用全部内联 |
| **代码重复** | createCrossSheetPanel 和 createDuplicateColPanel 中的文件选择、进度条创建、SwingWorker 模式高度相似 |
| **硬编码** | `L1508`：`targetHeader.equals("手机号码")` 决定合并格式，无法扩展 |
| **脆弱的组件引用** | `L1224-L1225`：通过 `(JLabel)((JPanel)progressDialog.getContentPane().getComponent(0)).getComponent(0)` 获取进度标签，布局变更即崩溃 |
| **废弃 API** | `L16`：`XMLReaderFactory.createXMLReader()` 已废弃 |
| **L671 readXLSHeaders()** | `WorkbookFactory.create(fis)` 返回的 workbook 未在 finally 中关闭，异常路径下会泄漏 |

### 2.3 安全问题

| 位置 | 问题 |
|------|------|
| `L632` readXLSXHeaders() | `OPCPackage.open(fis)` 打开后在异常路径下可能未关闭（pkg.close() 在 finally 块外） |
| `L640` | SAX 解析设置了 XXE 防护但仅 warn 级别，设置失败不会中断解析 |
| `L671` readXLSHeaders() | workbook 未在 finally/try-with-resources 中关闭 |
| 全局 | 无路径遍历校验，用户可选择任意文件路径进行读写 |

### 2.4 代码规范问题

| 问题 | 位置 |
|------|------|
| 异常被吞掉 | L2068：`catch (Exception e) { e.printStackTrace(); }` 在 main() 中 |
| `L646` | XXE 防护设置失败仅 `logger.warn()`，应为 `logger.error()` 或抛异常 |

## 三、TOP 5 优先优化点

### 优化 1：拆分 ExcelTools.java（2074 行 -> 多个类）

**现状**

一个类包含 5 个 Tab 的全部逻辑。`createCrossSheetPanel()` 单个方法 300 行，`createDuplicateColPanel()` 150 行，`addProcessorPanelEventHandlers()` 215 行。

**优化方案**

```
com.xzy
├── ExcelTools.java              ← 仅保留主窗口框架 + Tab 容器 (~200行)
├── panel/
│   ├── ProcessorPanel.java      ← Excel处理器 Tab (UI + 事件)
│   ├── MappingPanel.java        ← 建立映射关系 Tab (UI + 事件)
│   ├── ApplyPanel.java          ← 应用映射 Tab (UI + 事件)
│   ├── CrossSheetPanel.java     ← 跨表填充 Tab (UI + 事件)
│   └── DuplicateColPanel.java   ← 重复列合并 Tab (UI + 事件)
├── service/
│   └── ExcelProcessService.java ← processExcel() + applyMapping() 核心逻辑
├── model/
│   └── HeaderMapping.java       ← 数据模型 (从内部类提取)
└── util/
    └── ExcelUtils.java          ← getCellValueAsString() + copyCellValue() + readHeadersOnly()
```

**收益**
- 单个文件从 2074 行降到 200 行以内
- 各 Tab 独立修改，降低回归风险
- 核心逻辑与 UI 解耦，便于后续测试

**风险：** 中。需处理组件间依赖（如 logArea 被多个 Tab 共享、mappingRelations 在 MappingPanel 和 ApplyPanel 间共享）。建议通过构造函数注入共享状态。

**优先级：** P2 | **预估工作量：** 4-6 小时

### 优化 2：修复 applyMapping() 的内存和性能问题

**现状（L1011-L1199）**

- 使用 `XSSFWorkbook` 全量加载到内存，大文件会 OOM
- 每行调用 `SwingUtilities.invokeLater()` 更新进度，10 万行 = 10 万次 EDT 调度
- 输出也用 `XSSFWorkbook`，未使用 SXSSF 流式写入

**优化方案**

- 读取改用事件模型（SAX）或分批读取
- 写入改用 `SXSSFWorkbook` + `flushRows()`
- 进度更新改为每 1000 行批量更新一次（与 processExcel() 的 BATCH_SIZE 保持一致）

**收益**
- 处理大文件时内存占用从 O(n) 降到 O(100)
- 消除接近 1000MB 文件时的 OOM 风险
- UI 不再因高频 EDT 调度而卡顿

**风险：** 中。SXSSFWorkbook 不支持随机读写已刷出的行。当前 applyMapping 的"读取-复制-填充-写入"流程需要调整为"逐行读取-逐行写入"模式。

**优先级：** P1 | **预估工作量：** 2-3 小时

### 优化 3：消除 processExcel() 中的 O(n*m) 查找

**现状（L1343）**

```java
// 内层循环中每次都线性查找
int targetColumnIndex = templateHeaders.indexOf(mapping.getTargetHeader());
```

每个映射的每行数据都执行一次 `indexOf()`，复杂度 O(映射数 * 行数 * 模板列数)。

**优化方案**

在循环外预建 `Map<String, Integer> templateHeaderIndexMap`：

```java
Map<String, Integer> templateHeaderIndexMap = new HashMap<>();
for (int i = 0; i < templateHeaders.size(); i++) {
    templateHeaderIndexMap.put(templateHeaders.get(i), i);
}
// 内层循环中
int targetColumnIndex = templateHeaderIndexMap.getOrDefault(mapping.getTargetHeader(), -1);
```

**收益**
- 查找从 O(m) 降到 O(1)
- 处理 10 万行 * 20 个映射 * 50 列模板时，减少约 100 亿次比较

**风险：** 低。纯算法优化，不改变业务逻辑。仅需注意 `getOrDefault` 返回 -1 时的处理（当前已有 `>= 0` 判断）。

**优先级：** P0 | **预估工作量：** 10 分钟

### 优化 4：修复资源泄漏和废弃 API

**现状**

| 位置 | 问题 |
|------|------|
| L632 | `OPCPackage.open(fis)` 在异常路径下未关闭 |
| L671 | `WorkbookFactory.create(fis)` 未在 try-with-resources 中 |
| L16 | `XMLReaderFactory.createXMLReader()` 已废弃 |

**优化方案**

```java
// L632: 改为 try-with-resources
try (FileInputStream fis = new FileInputStream(file);
     OPCPackage pkg = OPCPackage.open(fis)) {
    // ...
}

// L671: 改为 try-with-resources
try (FileInputStream fis = new FileInputStream(file);
     Workbook workbook = WorkbookFactory.create(fis)) {
    // ...
}

// L640: 替换废弃 API
XMLReader parser = javax.xml.parsers.SAXParserFactory.newInstance()
    .newSAXParser().getXMLReader();
```

**收益**
- 消除文件句柄泄漏风险
- 消除编译器废弃警告
- 长时间运行时不会因句柄耗尽而崩溃

**风险：** 低。标准的资源管理修复，不改变业务逻辑。

**优先级：** P0 | **预估工作量：** 30 分钟

### 优化 5：消除硬编码和脆弱引用

**现状**

| 位置 | 问题 |
|------|------|
| L1508 | `targetHeader.equals("手机号码")` 硬编码决定合并格式 |
| L1224-L1225 | 通过 `getComponent(0)` 硬编码层级获取进度条组件 |

**优化方案**

**手机号码硬编码：**
- 方案 A：在映射配置 UI 中增加"合并格式"下拉框，让用户选择
- 方案 B：改为基于正则/关键字列表配置，从配置文件读取

**脆弱的组件引用：**
- `createProgressDialog()` 返回 `JDialog`，但调用方需要从中提取 `JLabel` 和 `JProgressBar`
- 改为返回一个 `ProgressDialog` 包装对象：

```java
private static class ProgressDialog {
    JDialog dialog;
    JLabel label;
    JProgressBar progressBar;
}
private ProgressDialog createProgressDialog(String title) { ... }
```

**收益**
- 手机号码逻辑可配置化，新增类似字段无需改代码
- 进度对话框引用从脆弱的 `getComponent()` 链改为类型安全的字段访问
- 布局调整不再导致运行时 ClassCastException

**风险：** 低。ProgressDialog 包装类是纯内部重构。手机号码配置化需要新增 UI 控件，有一定工作量但无运行时风险。

**优先级：** P1 | **预估工作量：** 1-2 小时
